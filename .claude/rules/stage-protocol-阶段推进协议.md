# 阶段推进协议

本项目按**阶段**推进（S1…S16…，权威清单在 `.claude/plan/status.md` §3.2）。
长会话里上下文会被压缩，所以**不依赖记忆**：每阶段的输入、验收、落地都写在文件里，按下面的
「读 → 做 → 写」走，任何一轮都能无损接手。

> **与用户级技能的关系**：本文件是**本项目实例**，只写本项目特有的路径、命令与约束。
> 通用方法（三锚点 / 计划文件分工 / 跨层重复判据 / 防退化检查项）见**用户级技能 `plan-tracking`**。
> 措辞允许重叠，但**同一段不得两边规定不一致**；方法变更**先改技能，再同步本文件** —— 方向唯一。
>
> **为什么重叠不是缺陷（2026-09-13 复核）**：① 协议必须从**确定性入口**进入 —— 本文件靠 `paths`
> 匹配触发（到点必读），而技能是**模型按需调用**、不保证每阶段开工都被读到；② 本文件**入库**，
> 用户级技能在同步盘、**不在仓库里**。故四步 / 铁律 / 六步 / 汇报格式按「通用规范 + 本项目实例」并存。

## 开工四步（重新加载阶段性目标，别省）

1. `.claude/plan/stages.md` §9 **断点卡** → 找到「下一步开工点」，**本阶段只做这一件事**；
2. `.codebuddy/memory/MEMORY.md` → 长期事实（口径决策、U 系列差异、踩过的坑）；
3. 根 `AGENTS.md` → 硬约束 C1–C5；
4. `.claude/plan/status.md` §3.2 状态表 → 各阶段 ✅/⏳ 与门槛数字；并跑一次门槛确认基线
   （命令见 `status.md` §3.1）。

四者矛盾时**以断点卡（`stages.md` §9）为准**，并顺手把另外两处改对 —— 信息不一致本身就是缺陷。

## 阶段内铁律

- 一次只推一个阶段；**边界不可讨价还价**：需要新设计的大改，先把它写成断点卡里的新阶段
  （目标 + 验收）再开工。
- 验收只看门槛（`pytest -q` 的数字 + fixture 逐字节一致）；「看起来对了」不算结论。

## 收工六步（落地处理结果，缺一不可）

1. 门槛跑绿；
2. 刷新 `.claude/plan/stages.md` §9 断点卡：本阶段结论 + **下一步开工点** + 残留（含「为什么不修」）；
3. 更新 `.claude/plan/status.md` §3.2 状态表：阶段标 ✅、填新门槛；
4. `.codebuddy/memory/MEMORY.md` 只沉淀**长期事实**（新口径 / 新约定 / 新坑），不留过程；
5. 追加 `.codebuddy/memory/<今天>.md` 当日记录（缺口 / 原因 / 证据 / 残留）；
6. 提交：一个阶段 = 一个（或一组能一一 revert 的）提交；含**不可逆动作**必须写「回退方式」；
   **提交消息不要带 ASCII 引号或反引号**（PowerShell 会吞 → 提交静默不执行）。

**汇报格式（固定）**：`缺口 → 原因 → 改动 → 证据 → 验收（数字） → 残留 / 下一步`（与阶段卡同构，省「回退方式」；
字段含义与「旧称对照」见用户级技能 `plan-tracking`）。它展开自全局汇报骨架四项不变量：
**背景 / 改动 / 结果 / 待办**（`缺口 → 原因` = 背景，`证据（修复前 → 修复后对照）` = 结果主体、`验收（数字）` = 证据子条目，`残留 / 下一步` = 待办）。

**阶段短名**：每个阶段 = `S<n>` + 短名（≤ 8 字），短名定在 `status.md` §3.2 状态表的「内容」列与阶段卡标题
`### S<n> <短名>`；**引用一律写 `S<n>（短名）`**，范围引用（`S1–S16`）靠状态表兜底。
